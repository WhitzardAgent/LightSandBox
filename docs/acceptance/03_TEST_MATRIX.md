# 测试矩阵与反虚假通过规则

## 测试层次

| 层 | 运行条件 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 文档包检查 | Python标准库 | 任务依赖、引用、状态和包完整性 | 沙盒已实现或安全 |
| 静态/单元 | 无特权开发环境 | 数据校验、状态机、依赖方向 | Linux实际隔离 |
| 真实运行时 | 授权专用VM | runc、进程、mount、网络、限额实际行为 | 所有任务兼容 |
| 差分 | 固定Docker/OpenSandbox参考 | 同一输入的协议和运行语义一致性 | 模型解题率 |
| 全量任务 | 固定任务资产和验证器 | 逐任务环境/验证兼容 | 未测试发布或平台 |
| 安全/故障 | 独立可恢复worker | 所测边界和故障处理 | 任意漏洞免疫 |
| 性能 | 受控重复试验 | 所测负载下延迟/密度/吞吐 | 未测机器上的保证 |

每个任务卡列出具体用例编号、前置条件、操作与可观察结果。用例由 `specs/test-catalog.json`管理，集成者核对测试实现与编号映射。编号存在不代表代码已实现。

## 必须有的负控

候选API返回成功但无实际进程、验证器没有执行却存在旧结果文件、任务发生oom但被当作普通失败、跳过零测试、错误patch或PoC被判成功，都应有故意注入的检测用例。参考和候选不能共用同一个未经验证的错误解析器后互相“证明”。原始官方结果与独立提取器交叉核对。

## 故障注入边界

区分客户断线、API服务重启、节点服务重启、exec broker死亡、worker VM重启。只有在真实注入该层故障并验证之后才声明该层恢复。PID、mount或socket名相同不代表资源是原对象，必须检查generation/所有者及启动标识。

## 覆盖不等于文件行覆盖

重点覆盖权限变化、资源耗尽、并发删除、文件路径替换、TTY断线、跨sandbox访问、老token复用、DNS重绑定、镜像损坏和重复请求不确定窗口。`cargo test`绿色无法代替这些系统测试。

## 回归策略

开发者先跑相关用例，再跑无特权完整suite。合并门禁根据修改路径选择真实运行时/差分/安全测试；相关必需测试不可用时标记BLOCKED并阻止合并。全量基准在预定里程碑和发布前执行，避免每次微小改动都付出全量成本。

修改公用协议、状态机、rootfs或网络策略，需要扩大回归范围；修改判分/汇总器必须执行负控与完整历史结果重算。测试选择器本身受到测试和审查。
