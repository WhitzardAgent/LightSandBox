# 高密度与吞吐验证计划

“更轻”和“显著加速”是待验证假设。Docker已有只读层和页缓存共享，不能把这些机制本身作为相对优势证据。[S12]

## 基线从第一条真实链路开始

T05建设测量器，T08开始记录候选基线。T29在正确性稳定后优化。分别记录导入镜像、已缓存镜像创建、冷缓存创建、exec启动、日志读取、PTY交互、删除请求接受与实际回收完成。冷热缓存条件明确，不以候选warm对比参考cold。

三方使用相同宿主资源、镜像digest、任务脚本、网络、文件系统driver、日志策略与安全profile。生产运行无Docker的声明与测试机允许Docker参考不冲突，但每次测量需隔离互相干扰。

## 四种规模

空环境、驻留空闲、轻量并发工具调用、真实编译/测试活跃任务分别测。对每组逐渐增加并发，记录排队、拒绝、超时、oom、实际有效任务/秒。高驻留数量不能替代高有效吞吐。

内存使用整机增量和cgroup实际计费，并辅以PSS/USS；不能简单相加RSS导致共享页重复计算。单独报告节点服务、broker/init、任务进程、页缓存、FUSE/CNI和文件系统元数据。cgroup内存计费可能受首次访问归属影响，需要保留测量方法。

## 调度模型

一个host维持全局admission预算：CPU、内存、PID、FD、磁盘、spool字节、网络连接、镜像解压与构建并发。优先保证已准入任务，使用有界队列和背压。按tenant/profile和任务成本公平调度，不能由单个大量日志任务耗尽节点。

agent等待模型期间仍可能有后台进程和持久状态，不能自动freeze而改变语义。主动idle/freeze策略必须显式启用并通过差分测试；freeze不释放已有RAM。真正释放内存并保留进程需要其他机制，v1不承诺。

## 实验输出

每项给出硬件/虚机规格、CPU配额、内核与工具版本、cache状态、样本数、到达模型、重复轮次、原始数据、分位数/置信区间、错误率和资源残留。选择优化时同时比较真实任务耗时和p99长尾，避免只优化空sandbox创建。

## 优化候选与守护条件

1. 减少每sandbox常驻服务：先测tiny init和共享broker，再决定是否需轻量helper。不得损坏PTY/reconnect。
2. 复用不可变镜像与安全的预制rootfs：禁止复用含旧租户状态的写层。
3. 缓存解析结果与控制面连接：绑定digest/generation，避免缓存越权。
4. 合并元数据写入和削减fork/CLI次数：保留崩溃窗口语义和审计。
5. 分离构建/镜像准备/活跃执行预算：公平性与完整任务兼容回归必须保留。

不在规划中预填毫秒数、每sandboxMB数或每台VM数量。性能门槛在T05得到初始可重复基线后登记为可测试SLO，目标变更保留审批与历史值。
