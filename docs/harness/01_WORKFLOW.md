# 开发代理工作流

这里的harness指让Coding Agent稳定开发本项目的任务、上下文、工具、测试与审查机制，不是评测引擎，也不引入新的通用agent编排平台。

## 角色与循环

初始化会话完成T00，并为T01–T03建立可执行入口。之后每次会话选择一个依赖满足的任务卡；先查代码与现有测试，再写局部执行计划。用当前缺口的失败测试驱动实现，运行相关检查和无特权完整suite，最后提交给独立评审。跨会话状态保存在Git和结构化文件中。[S03][S05]

任务卡是一次可独立审查的交付边界。卡内若出现两个可分别验收的功能，实施前拆为子卡并更新catalog；不能用“一个任务”名义进行无限范围改造。最多一个主任务处于本会话active状态，发现的相邻问题进入issue/决策记录。

## 第一条纵向链路

先实现可运行的最小服务，不先生成几十个空crate和几千行占位接口。T00建立四crate依赖边界和真实检查；T08必须让最小API调用经过真实runc完成create/exec/delete。后续逐步加入能力，始终保留一个可以复现的运行入口。

## 每次任务的七步

1. `packctl validate/next/context`，检查Git工作树，读任务与必要设计。
2. 记录当前事实、差异与最小测试，获得所需测试节点权限，不自动提权。
3. 运行失败测试，确认失败原因对应缺失行为；环境缺失标BLOCKED。
4. 完成最小实现，避免非本任务重构和依赖膨胀。
5. 跑相关测试、完整无特权suite与要求的真实/差分测试。保留全部失败，不只报最后一次绿灯。
6. 由新上下文评审检查spec和代码、原始证据；集成者决定verified。
7. 写交接与下一条可执行命令。未完成时明确停点、资源状态和未关闭风险。

## 自主推进与停止条件

同一授权范围内，依赖满足、测试资源可用、当前门禁通过时，可以继续下一任务，无需每个小步骤请求确认。更改安全边界、完整任务范围、外部API合同、生产数据或宿主安全策略时必须升级决策，不能擅自改变。

连续两次针对同一失败的补丁无证据进展时，停止猜修，建立最小复现、检查资源/日志与对应规范。缺少资料先读取真实来源；无法获得时保留明确blocker，转到另一个独立就绪任务。限制循环成本，不运行无人监管的无限自动重试。

## 回归与文档维护

每次确认一种通用失败模式，添加最小回归和简短说明。接口改变同一提交更新文档/类型/调用者；变更受影响路径决定回归范围。文档修改本身不提升产品完成度。
